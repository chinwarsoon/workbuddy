6.3 一个务实的架构建议

如果这是一个自建项目，最容易失败的架构是"做一个大平台"。更可行的做法是一个共享数据层 + 若干薄应用：

层内容技术取向
主数据层Project、WBS、Discipline、Package、EquipmentTag、DocumentId、Person/Role、System/Subsystem关系型数据库 + 稳定的 ID 策略（标签编号是命脉）
事件层状态变更、接口关闭、资料收到、变更登记——全部为不可变事件事件表 / append-only log，保证可审计与可重放
视图层每个应用本质上是同一个数据层的一个"视角"薄前端；避免在应用间复制数据
集成层CDE（文档）、P6（进度）、工时系统、ERP/采购、BIM 模型以"ID 对账 + 定时同步"为主，API 为辅；CSV 兜底
分析层挣值、S 曲线、根因分布、就绪度在数据层上直接算，不做二次录入
为什么强调 append-only

工程管理工具最大的隐性价值是争议时的举证能力。如果"接口关闭日期"可以被覆盖，那它在索赔桌上就没有价值。不可变事件流让每一次状态变更都带时间戳与责任人，这与 CDE 的"数据不可变"设计逻辑一致，也是本报告把 A04 与 A07 设计成事件驱动的原因。

07 — SPECIFICATIONS

十二个应用规格

每个规格包含：要解决的精确问题、核心数据对象（字段级）、关键交互与规则、MVP 范围、以及一个能被验证的成功指标。点击展开。数据模型用类 TypeScript 伪类型表达，便于直接转成实现。

A01

Design Basis Manager · 设计基础与假设登记

把"我们假设了什么"变成一等公民，并让每个假设可以反向查询它影响的所有交付物

 ▶
要解决的问题

设计基础通常是一份 Word 设计说明加几个 Excel 表。它有三个致命弱点：假设不可见（读者不知道哪些是实测、哪些是猜的）、变更无传播（改了峰值因子，没人知道要重算哪些东西）、无法举证（争议时无法证明"这是业主给的数据"）。

关键设计决策

引入 Assumption 作为独立对象，与 DesignBasis 平行。每个假设必须有置信度、验证方法与影响面。这不是文档管理的思路，而是风险登记的思路。

成功指标
  • 假设闭环率 ≥ 90%（在 IFC 前完成验证或书面接受）
  • 因假设变化引发的返工工时占比 < 3%
  • 任一交付物可在一分钟内追溯其依赖的全部假设
核心数据模型
// 设计基础（版本化，一版一冻结） DesignBasis { id, project_id, revision, status, // draft | issued | approved flow: { avg, peak_hour, peak_factor, min, wet_weather }, loads: { BOD, COD, TSS, TN, TP, FOG, metals[], NH3N }, temperature: { min, max, seasonal }, alkalinity, pH_range, sulphide, source_refs: DocumentId[] // 数据来源 } // 进水表征：分布而非单值 InfluentProfile { stream, parameter, unit, stat: p50|p95|max|min, sample_count, period_from, period_to, method: // SM / EPA / ISO 条款 dataset_ref // 原始数据 } // 假设：本项目最重要的对象 Assumption { id, statement, category, basis: // 实测 / 类比 / 规范默认 / 业主提供 confidence: 1..5, validation_method, validation_date, owner, status, impact_if_wrong: { cost_impact, schedule_days, affected_deliverables: DeliverableId[], affected_equipment: TagId[] } }
MVP 范围

先做三件事：① 结构化 DesignBasis 与 InfluentProfile；② Assumption 登记与依赖挂靠；③ 一页"设计基础卡片"导出 PDF 供合同与设计交底使用。暂不做：自动采样数据接入、与模拟软件双向同步（放到 A09）。

A02

Deliverable Register · 交付物登记与阶段闸门

让"完成"有定义：不是谁说了算，而是过了哪道闸门、有谁签、有什么证据

 ▶
要解决的问题

典型的 MDR 是一张长表，有编号、名称、专业、计划日期、实际日期、状态。问题是状态是自由文本（"进行中""基本完成""待审"），而"基本完成"对不同的人意味着 40% 到 95%。

关键设计决策

用固定的状态机 + 可配置的闸门替代自由文本。状态只允许沿 NotStarted → InProgress → Checked → IFR → IFA → IFC → AFC → AsBuilt 前进，每跳一次必须满足该阶段的检查清单并有签署人。跳步被系统拒绝。

成功指标
  • IFC 准时交付率（±5 天窗口）≥ 85%
  • 平均评审周转 ≤ 10 个工作日
  • 阶段闸门跳步事件 = 0（硬性）
核心数据模型
Deliverable { id, code, title, discipline, deliverable_type, // Drawing / Calc / Datasheet / Spec / Report package, system, wbs_code, budget_hours, weight_in_discipline, planned: { start, ifr, ifa, ifc, afc }, actual: { ... }, responsible, checker, approver, status, current_stage, depends_on: DeliverableId[], depends_on_vendor_docs: VendorDocId[], cde_ref: DocumentId } Stage { name, weight_pct, // 阶段权重 required_checklist: ChecklistId, min_reviewers, signed_by[], actual_date, evidence: link[] } GateCheck { deliverable_id, stage, items: [{ question, pass|fail|na, evidence_ref }], blocked_by: [], // 未闭合的接口/资料 released_at, released_by }
MVP 范围

Register + 状态机 + 阶段权重 + 与 CDE 的文档链接。先在一个专业（建议：工艺或机械，交付物数量适中、接口多）试点，验证闸门不会变成新的瓶颈。不做：自动从 BIM 提取交付物清单。

实施陷阱

闸门过严会把工程师逼到系统外——他们会先在 Excel 里干完，再一次性录入。必须让"录入"与"干活"是同一个动作：在设计文件命名、提交到 CDE 时自动触发状态推进，而不是要求额外填报。

A03

Earned Value Engine · 阶段权重挣值

用"哪一个里程碑被达成"来计量进度，而不是"工程师觉得自己完成了多少"

 ▶
要解决的问题

工程进度长期靠自评百分比。这类数字无法用于收款、无法用于预测、也无法指出哪些交付物真的有风险。而施工阶段早已用挣值解决这个问题：进度不是意见，而是"哪些物理里程碑已完成、它们带多少预算"。

核心公式
// 挣值工时：由事件推导，不由人填写 EarnedHours(d) = Σ ( d.budget_hours × d.stages.achieved.weight_pct ) // 三个数必须同时存在才有意义 Budget = Σ d.budget_hours // 基准 Actual = Σ timesheet.hours // 实耗 Earned = Σ EarnedHours(d) // 挣值 SPI = Earned / Planned CPI = Earned / Actual EAC = BAC / CPI
成功指标
  • 超支预警提前期 ≥ 4 周（在 CPI 跌破 0.95 前发出）
  • 进度报告与现场实测偏差 < 5%
  • 所有计量收款有可追溯到交付物的依据
三条读数规则

实际 > 挣值 → 生产率低于计划，团队花得比挣得多。

挣值 > 实际 → 生产率高于计划，可以借调资源或加速。

预算消耗快于挣值积累 → 该专业正在走向成本超支，且这个信号会早于进度延误出现。

关键集成
  • 工时系统：按交付物（而非按人）记录工时
  • P6：工程活动作为 WBS 段，与交付物建立映射
  • 商务：计量支付节点引用交付物阶段
MVP 范围

以专业为单位的周度 SPI/CPI + 一张 S 曲线。工时按交付物归集的准确度是难点——初期可允许"按交付物类别分摊"，但必须在三个月内过渡到逐交付物记录，否则挣值退化为估算。

A04

Interface Register · 接口承诺与关闭证据

把专业之间"我以为你会给我"变成有责任人、有到期日、有关闭证据的可审计记录

 ▶
要解决的问题

多数多专业 EPC 的失败不是明显的技术错误，而是当一方假设另一方会在某天之前提供数据、空间、容量、通道、电源、支承、控制或批准，而这个依赖没有被显式化。每个专业都可以显得局部完整，而整合后的项目无法建造、无法试验、无法运行。

关键设计决策

接口点必须由设计人在设计阶段创建，而不是在施工现场被发现。接口必须绑定到期日与"迟到的后果"，否则只是清单。接口关闭必须有证据——图纸批准、安装完成、试验通过，三者之一，不能是"已沟通"。

成功指标
  • 接口按期关闭率 ≥ 90%
  • 施工期新发现的接口数量 < 总数的 10%
  • 因接口导致的变更数量同比下降 50%
核心数据模型
InterfacePoint { id, project, type, // Hard: 物理/电气/管道/信号 // Soft: 数据/参数/逻辑/规范 from_party, to_party, disciplines: Discipline[], description, // 交换什么，精度多少 required_date, status, // Open/Agreed/Delivered/Verified/Closed consequence_if_late: { activity_id, days_of_float, cost_impact }, evidence: Evidence[], // 关闭必须有 ref_deliverables: DeliverableId[], ref_tags: TagId[], ref_model_elements: ElementId[] } InterfaceAgreement { parties: Party[], scope_split, // 谁做什么，到哪为止 acceptance_criteria, signed_at, version } InterfaceQuery { ip_id, raised_by, question, response, responded_at, closed_at, closed_by }
污水厂的高频接口清单（可直接用作初始模板）
硬接口交换内容迟到的典型后果
设备 ↔ 基础/结构荷载、动载、预埋件、地脚螺栓位置、检修空间基础浇筑后无法改，现场凿改或加固
机械包 ↔ 电气供电容量、启动方式、电缆路径、MCC 回路电缆规格错误或桥架不够
电缆路由 ↔ 结构桥架穿越、开孔位置、载荷结构开孔影响配筋与抗渗

A05

Procurement–Engineering Link · 长周期项与设计成熟度联动

下单不只看日期，还要看设计是否成熟到能锁定接口

 ▶
要解决的问题

长周期设备有一个双向依赖：设计必须成熟到能下单，下单后又需要供应商资料才能继续设计。如果这个往返没有被计划为"双向前置"，项目会出现隐蔽僵局：设备在路上，但土建、电气、自控都在等资料。

常见错误（可直接写进检查清单）
  • 在 RFQ 之后才识别长周期项
  • 把制造周期当作总周期（漏掉资料、检验、FAT、物流）
  • 在不冻结关键接口的情况下提前采购
  • 进度里没有供应商资料这一项前置
  • 只替换预测而不更新基线
  • 把"贵"等同于"关键"——低值但卡在联锁上的仪表可能更关键
核心数据模型
LLIItem { tag, package, system, lead_time_wks, // 仅制造 total_lead_wks, // 含资料/检验/FAT/物流 required_on_site, // 现场需要日期 acceptable_window, // 早到也是风险 requisition_date, award_date, vendor_data: [{ doc_type, required_by, received }], fat_date, ship_date, float_wks, // 采购浮动余量 criticality: { // 不只按金额 schedule_dependency, replacement_difficulty, cert_exposure, transport_constraint, alternative_availability } } RequisitionGate { package, design_maturity_required, // 需达到哪一阶段 design_maturity_actual, // 实际 interfaces_frozen: [], // 必须已冻结的接口 released: bool }
成功指标

关键包采购浮动余量 ≥ 4 周；逾期关键供应商资料数 = 0；因设计不成熟导致的下单延迟天数逐季下降；关键项识别覆盖率 100%（在 MR 发出前）。

A06

Vendor Document Tracker · 供应商文件与意见闭环

让每一条评审意见都有 ID、有主人、有状态，并且永不丢失

 ▶
要解决的问题

供应商文件评审是 EPC 里最"钝"的环节：典型一轮 2–4 周，退回重交再增加 3–6 周。而真正让周期失控的不是评审时长，而是循环次数。一个 C 码往返三次，两个月就没了，即使所有人都守时。

最致命的小问题：意见丢失

"Rev B 里答复了、但 Rev C 里没有被验证"的意见，等于一条被丢失的意见，而丢失意见就是返工的开始。这必须在数据结构上解决：开放意见自动带入下一版，并在下一版强制逐条确认。

成功指标
  • 首次通过率（A/B 码）≥ 70%
  • 平均评审循环 ≤ 1.5 轮
  • 跨版本意见丢失 = 0（硬性）
核心数据模型
VendorDocument { vendor, po_ref, tag, doc_no, rev, doc_type, // Datasheet / GA / ITP / Calc / Manual required_date, received_date, review_cycle, review_code, // A 批准 / B 有意见批准 // C 修改重交 / D 拒绝 reviewer, returned_date, linked_deliverables: DeliverableId[], // 设计在等这份资料 deviations: Deviation[] } Comment { id, doc_id, rev, clause_ref, // 规范/图纸条款 severity, // Must / Should / Info category, // Safety / Tech / Compliance text, owner, status, // Open / Answered / Verified / Closed carried_to_rev, // 必须非空直到闭合 verified_in_rev, verified_by }
MVP 与自动化边界

MVP：文档登记 + 评审码 + 意见逐条状态 + 跨版本带入。不要一开始就做 AI 全自动审阅：先让流程可追溯。等意见库积累到一个项目的量（通常 2,000–5,000 条），再把"资料表 vs 项目规范"的偏差检查交给 AI 做初筛，人只做判断。

A07

Change & RFI Intelligence · 变更与 RFI 的因果结构

不问"改了什么"，而问"为什么会改、谁的责任、能不能不再改"

 ▶
要解决的问题

大多数变更台账记录"变更描述、金额、时间"，但不记录根因分类。后果是双重的：争议时无法分离"承包商责任"与"业主/设计责任"；管理上无法知道下一次该在哪防。

关键设计决策

每条 RFI 与变更必须打上两个标签：root_cause 与 avoidable。这两个字段是整个系统的"学习接口"——它们直接决定 A08 要新增什么检查项、A12 要写什么规则。

根因分类（建议直接用）
  • 图纸跨专业冲突
  • 尺寸缺失或前后不一致
  • 规范/材料等级未覆盖
  • 业主需求变更
  • 供应商偏差（数据表不符）
  • 现场实际条件与图纸不符
  • 设计基础假设变化
  • 法规/许可条件变化
核心数据模型
ChangeEvent { id, type, // DesignChange/Variation/FieldInstruction trigger, root_cause, // 见左列分类 avoidable: bool, discovered_at_stage, // Design / Procurement / Construction / Cx affected_deliverables: [], affected_packages: [], affected_interfaces: InterfaceId[], cost_impact, time_impact_days, responsibility, // Contractor/Owner/Vendor/Third party evidence: [], // 同期记录，决定举证成败 linked_rfi: RFIId } RFI { id, question, raised_by, discipline, system, avoidable, root_cause, days_open, answer_at, design_response_owner, resulted_in_change: bool }
成功指标

RFI 密度（条/百万元）季度下降；可避免比例从 30–60% 降到 20% 以下；设计原因变更占比下降；每条变更都能在一分钟内给出"根因—影响—责任—证据"四要素。

组织阻力

工程师不愿意承认某条 RFI"本可避免"。解法是把 avoidable 定义为系统属性而非个人过失：它标记的是"图纸集当时不具备回答条件"，用于改进检查项，不进入个人考核。这一点必须在推行时说清楚，否则数据会立刻失真。

A08

Cross-discipline QA Gate · 跨专业校审与图纸集自洽

审核每张图都对、合起来错的地方——也就是专业之间的那些位置

 ▶
要解决的问题

传统审图按专业分工进行，于是跨专业冲突恰好是存活到现场的那一类。每一项单独检查都正确，但组合起来是错的——因为没有任何一个人拥有两张图之间的空间。

三类检查（按投入产出排序）
  1. 参数一致性：同一设备在不同文件里的参数是否一致（数据表 vs 布置图 vs P&ID vs 单线图）。这是最容易自动化、收益最高的一类。
  2. 图纸集完整性：缺失尺寸、图号交叉引用断链、被引用但未绘制的详图。
  3. 空间与净空：模型碰撞、检修通道、吊装路径、阀门操作空间。

污水厂要特别关注：池内回流管、曝气支管、仪表线槽三者的空间冲突；以及设备吊装孔与顶部净空。

核心数据模型
ReviewChecklist { discipline, stage, items: [{ id, question, mandatory, evidence_type, auto_checkable }] } SetCompletenessFinding { drawing_set, type, // missing_dimension // cross_ref_broken // param_mismatch // spec_orphan location, severity, owner, resolved_at } ClashIssue { model_a, model_b, element_a, element_b, location, clearance_required, severity, owner, resolved_at, resolution }
成功指标

IFC 发布前严重冲突数 = 0；图纸集自洽缺陷数逐版下降；首轮评审通过率提升。注意：这类工具的收益必须用"避免的 RFI 与返工"来度量，而不是用"发现的冲突数"——发现得多不代表好。

A09

Process Design Workbook · 工艺设计工作簿与保守度监控

让每一个工艺数字都能追到它的计算、它的假设，以及它最终变成了哪台设备

 ▶
要解决的问题

工艺计算在 Excel、模拟在 BioWin/GPS-X、选型在数据表、P&ID 在 CAD——四者之间靠人记。结果是：改了回流比，没人知道要重算哪些池子；业主问"为什么这个池子这么大"，答不上来；设计院为求快而"拔高设计"，无人监控。

最有价值的功能：保守度监控

把 FEED 基准与详细设计的每个关键参数并排对比（池容、停留时间、风机风量、泵扬程、管径），自动标出放大比例超过阈值的项。这不是省钱技巧，而是利润保护：行业实践明确指出，"拔高设计"是普遍现象且需要被监控纠正。

成功指标
  • 关键计算书 100% 可追溯（输入→公式→输出→设备）
  • 设计余量分布可视化，超阈项 100% 有书面理由
  • 能耗强度（kWh/m³）在同类项目基准区间内
核心数据模型
CalculationSet { id, unit_process, // 如 A2O/二沉/消毒 inputs: { param, value, unit, assumption_ref }, formula_ref, // 规范条款或文献 outputs: { param, value, unit }, version, engineer, checked_by, design_basis_rev } ModelRun { software, version, // BioWin/GPS-X/SUMO scenario, influent_profile_id, calibration_source, results: { effluent, energy, sludge, chemicals }, run_date, engineer } SizingLink { calculation_id → equipment_tag → datasheet_id → p_id_ref } ConservatismCheck { parameter, unit, feed_value, detailed_value, ratio, threshold, // 如 1.15 justification, approved_by }
MVP 范围

先做 CalculationSet 的结构化登记与 SizingLink，再补 ConservatismCheck。不要试图重写模拟引擎——BioWin/GPS-X 的机理模型已经被行业验证三十年，自研没有胜算。这个应用的定位是"模拟的记账本与追溯层"。

A10

Commissioning & Turnover · 调试就绪度与生物启动

把"系统能否启动"从会议上的判断，变成一张实时的就绪度视图

 ▶
要解决的问题

调试期最典型的现象是：最后一两周才发现某个系统缺一个回路校验、缺一份 FAT 报告、缺一台仪表的校准证书，于是整个启动顺序被打乱。而污水厂还有一个别的资产没有的问题——生物启动不可压缩。

污水厂特有的两个数据对象

启动曲线：进水量按周爬坡（如 25% → 50% → 100%），伴随 MLSS、SVI、F/M、DO 的每日记录。接种记录：污泥来源厂、运输量、运输条件（需曝气）、接种比例。这两件事决定了能否在合同期内达标，必须有数据支撑而不是口头汇报。

成功指标
  • 系统就绪度在启动前 4 周可见且可预测
  • ITR 完成率曲线无末端突刺（说明证据是逐步积累的）
  • 性能试验一次通过
  • 移交包在机械竣工时已 80% 就绪，而非事后拼装
核心数据模型
System { id, name, boundary, subsystems: SystemId[], tags: TagId[], prerequisite_systems: [] } ITR { tag, system, test_type, // LoopCheck / Flush / Hydrotest // Function / Interlock / SAT status, signed_by, date, evidence: photo|pdf|data, result: pass|fail|conditional } PunchItem { location, category, severity, owner, due, verified_by, linked_itr } TurnoverPackage { system, certificates: [MC, RFC, RFSU], docs: [], // 图纸/手册/试验 outstanding_punch, accepted_at } // 污水厂特有 BiomassLog { date, MLSS, SVI, F_M, DO, feed_pct_of_design, seed_source, seed_volume, note }
关键设计决策：从设计期开始

系统边界（System/Subsystem）必须在设计阶段就定义好，因为它是接口、ITR、移交包、资产数据的共同骨架。如果等到调试期才划系统，意味着接口无法挂靠、资产无法归类。这也是 A10 不能推迟到项目后期的原因。

A11

Asset Data Handover · 资产数据移交

让业主继承一个可查询的资产数据库，而不是几十个纸箱

 ▶
要解决的问题

资产数据通常在设计、采购、施工、调试四个阶段被记录了四次，然后在移交时被重建第五次。结果是台账与现场不符，运维团队拿到的是 PDF 而非数据，尾款因资料不齐而滞留。

关键设计决策

资产台账必须是设计阶段的副产品，而不是移交阶段的产物。设备标签（tag）在数据表里生成时，资产记录就同时存在；供应商资料、试验记录、O&M 手册都挂到同一个 tag 上。

标准对接

若业主要求结构化交付，对齐 COBie 或 CFIHOS 一类的信息移交规范；若要求 BIM 资产模型，按 ISO 19650 的资产信息要求（AIR）组织。工具的价值在于一处录入、多格式导出，而不是手工填五张表。

成功指标
  • 资产数据完整率（必填字段）≥ 98%
  • 移交包一次验收通过
  • 移交周期缩短 50% 以上
核心数据模型
Asset { tag, class, // Uniclass/OmniClass description, system, location, manufacturer, model, serial, install_date, warranty_end, design_capacity, // 来自数据表 spare_parts: [], maintenance_interval, documents: DocumentId[], // O&M / 图纸 / 证书 test_records: ITRId[], model_element: ElementId } HandoverExport { format, // COBie / CFIHOS / JSON scope, // 全厂 / 单系统 completeness_report, validation_errors: [], generated_at }
与数字孪生的关系

不要从"数字孪生"倒推。行业经验反复显示，大多数数字孪生项目死在调试阶段，原因是从仪表盘开始，而不是从"需求 → 可验证的竣工信息 → 结构化资产数据 → 集成"这个顺序开始。先让资产数据可信，孪生是之后的自然延伸。

A12

Lessons & Design Rules · 教训转规则库

教训如果不变成检查项，它就不会被执行；执行不了，就等于没学到

 ▶
要解决的问题

每个项目结束都有一份"经验教训"报告，然后下一个项目重复同样的错误。原因不是大家不学习，而是教训停留在散文层——没有变成任何流程里的一个强制动作。

关键设计决策

每条教训必须转化成一个 DesignRule，而每条规则必须挂到具体的检查清单条目或校审提示上。无法转化的教训，允许只作为阅读材料，但要显式标注"未转化"，让这个比例成为管理指标。

成功指标
  • 教训转化率 ≥ 60%（进入检查项或规则）
  • 同类问题跨项目重复率逐年下降
  • 规则命中率可统计（哪条规则真的拦下过问题）
核心数据模型
LessonRecord { project, event_date, event, root_cause, cost_impact, rework_hours, schedule_impact_days, what_would_have_prevented_it, converted_to_rule: bool } DesignRule { id, rule_text, discipline, trigger, // 何时适用 check_type, // checklist / auto / ai_prompt linked_checklist_item, evidence_of_value, // 命中记录 owner, version }
为什么把它放在最后

A12 依赖 A07（根因）与 A10（调试教训）产生的数据。没有前两者的结构化数据，规则库只能靠访谈整理，质量低且不可持续。先让事件有结构，再谈沉淀。
